# SDK 版本与兼容约定

## 哪些值由厂商管理

厂商管理自己的**包版本和契约标识**。从样板开始开发时，将这些值替换为自己的产品信息；SDK 目标、C ABI 和 JSON 格式版本则沿用样板提供的受支持值，不随产品版本一起改动。

| 字段或名称 | 管理的对象 | 厂商如何处理 |
| --- | --- | --- |
| `provider.json.version` | 厂商自己的交付包 | 按自己的发布计划管理，并与 C++ 描述符的 `provider_version` 保持一致；样板为 `1.0.0` |
| `contract.json.contract_id` | 厂商输入契约的稳定身份 | 使用自己的契约标识，例如将样板的 `com.orca.examples.touch_grid.input.v3` 替换为自己的名称；它不是 SDK 版本 |
| `provider.json.sdk_version` | 生成输入结构和构建算法时选择的 SDK 配置，包含声明、能力语义和编译规则 | 当前使用 `"1.0.0"`，与构建时的目标保持一致；不要填厂商产品版本 |
| `abi_version`（包清单及 C 描述符） | C 调用接口和二进制结构布局 | 包清单保留 `2`；C 描述符使用公共头文件的 `ORCA_SENSOR_ABI_VERSION`，当前值同为 `2` |
| `contract.json.schema_version` | 输入输出 JSON 的声明格式 | 沿用当前格式 `4`；不要随包版本修改 |

**SDK 1.0.0 使用 C ABI 2。公共描述符和回调类型名中的 `V2` 就表示这套 C ABI**，例如 `OrcaSensorProviderDescriptorV2`。`V2` 不是 SDK 2，也不要求厂商包版本为 2。发布 SDK 新版本不意味着必须修改 C ABI；厂商修改算法或型号资产也不意味着 SDK 版本改变。

首次公开发布的 SDK 版本从 [VERSION](../VERSION) 读取，为 **1.0.0**，也是当前唯一支持的配置和默认基线。该基线包含完整能力集，包括接触力网格与 site 测距；Host 和契约工具的发布版本同为 **1.0.0**。首次公开发布不重置 C ABI 2、JSON RPC 1、契约 schema 4 或能力、契约 ID 中的协议编号。公开发布前的开发编号不是已发布版本，不属于对外兼容承诺。

场景名称前缀 `orca.sensor.v1/<实例>/...` 中的 `v1` 另行管理场景声明格式。它不要求 SDK 1，也不表示 C ABI 1；同一格式可以引用各个受支持 SDK 目标的型号，但型号的输入需求仍须符合所选绑定路径。

## 如何生成新包

使用样板的 CMake 构建时，输入头文件和包清单会自动生成，无需先手动执行工具；构建步骤见 [README](../README.md#5-构建并交付自己的型号包)。四个样板的源 `provider.json` 和 CMake 都已指定目标 SDK `1.0.0`。

同一个包的头文件生成器与清单生成器必须使用同一目标，动态库必须使用该目标生成的头文件构建。工具升级不能自动改变包的目标，也不能通过手改 `sdk_version` 绕过不兼容。

### 自建工程时可选：直接调用生成工具

如果自行编写构建流程，可以在完整 SDK 平台包的根目录运行以下命令，或将它们接入自己的构建系统：

```bash
bin/linux-x86_64/orca-sensor-tool contract examples/contact_grid/contract.json build/generated/contact_grid_input.h \
  --model examples/contact_grid/model.xml --mount-site sensor_base --sdk-version 1.0.0
bin/linux-x86_64/orca-sensor-tool provider_manifest examples/contact_grid/provider.json \
  build/providers/contact_grid/provider.json --sdk-version 1.0.0
```

以上命令使用 Linux x86_64 SDK 自带的工具，无需安装 Python。第二个子命令只生成清单，不复制模型、契约或动态库，不执行厂商代码，也不替代完整注册校验。它可以为尚未声明版本的源模板补上目标版本，但不能证明一个来源不明的旧动态库与该版本兼容。

查看工具版本可使用 `bin/linux-x86_64/orca-sensor-tool --version`；OrcaGym 中可使用 `python -m orca_gym.sensor.providers.cli --version`。CMake 生成的 `orca_sensor_version.h` 在构建和安装后均可引用，包含当前工具发布版本的 `ORCA_SENSOR_SDK_VERSION` 及其 major/minor/patch 宏；不能仅凭这些宏推断包选择的目标配置。

## 当前包如何选择基线

- 显式声明 `sdk_version: "1.0.0"` 的包，使用 1.0.0 的能力目录和编译规则。
- 未包含 `sdk_version` 的 ABI 2 包，按默认 1.0.0 基线校验；这不等于承诺兼容任意开发期动态库。新交付包应显式声明该字段。
- 明确填了未知版本、空值或非法版本的包，不会回退成 legacy；在打开厂商动态库之前拒绝。
- ABI 1 当前不受支持。SDK 版本声明不会绕过 ABI、输入指纹、布局、输出和类型描述符的检查。

兼容性由**已保留并验证的版本配置**决定，不是简单判断“厂商版本号小于运行时版本号”。尚未发布或尚未适配的未来版本不属于当前支持范围。

## 兼容不等于任何环境下数值完全一致

这里的兼容承诺是：在支持的运行环境内，Orca 按包声明的规则解释、组装和调用，不要求厂商因无关 SDK 升级修改包。

操作系统、CPU 架构、动态运行库和物理后端仍有各自支持范围。C ABI 避开 Python 扩展 ABI 依赖，不代表一个动态库可跨所有系统运行；同进程库也没有崩溃隔离。

相同输入序列、配置和 seed 下的算法重放，与更换物理引擎版本、求解器或硬件后的仿真数值复现是两项不同验收。兼容旧动态库不自动保证后者逐位相同。

## Orca 对已发布版本的兼容承诺

从首次公开版本 1.0.0 起，每个发布版本保留自己的配置与能力快照。新增能力应使用新的标识或新版本配置；不得修改旧版本下同一个能力的类型、单位、坐标含义等，再让旧动态库按新含义接收数据。

确需新增 ABI 或改变编译、模型解析规则时，新增独立处理路径，同时保留已承诺支持的旧路径；不得以升级主版本为由取消旧包兼容。旧包回归失败时，不应发布到仍承诺支持该旧包的运行环境。

### 随包资源与发布验证（Orca 维护者）

当前唯一配置 `compatibility/1.0.0/` 保存 `profile.json` 和完整能力快照，选择 `abi2-v1` 编译规则、`xml-v1` 对象解析规则，并校验快照的 SHA256。它是 Orca 维护、随交付物分发的冻结资源，厂商不自行编辑。未来新增版本须登记到工具的受支持版本表，保留独立配置与快照，不能仅改 `VERSION`、覆盖 1.0.0 或仅比较版本号大小。

发行时必须保留旧版本配置，并使用旧 SDK 生成和编译的真实厂商包做回归，而不是只用新工具重新编译一个“旧格式示例”。发布验收应冻结 1.0.0 的厂商二进制与来源记录，后续使用这些原始动态库校验：旧动态库能否注册、输入布局与指纹是否保持，以及计算、实例隔离、reset 和输出是否符合约定。每个目标平台分别保留并验证自己的基线二进制，不能把一个平台通过视为跨平台已验证。公开发布前的内部源码快照或开发期二进制只用于溯源，不代表已发布 SDK 兼容范围。

厂商 SDK 和支持插件的平台运行包必须包含所需 `VERSION`、兼容配置、冻结能力目录与匹配版本的工具二进制，均由 OrcaSensorHost 仓库发布。普通用户在支持平台上正常安装支持传感器功能的正式 OrcaGym 即自带 Host，不需另装 SDK 或 Runtime。OrcaGym 仅集成 Runtime，不维护第二份公共 SDK；完整演示由 OrcaPlayground 维护。厂商 SDK 另外提供公共 C 头文件、模板、手册和示例源码，不包含 Host 或生成/校验工具的内部实现源码。只有内部源码仓库能读到旧配置，而实际交付物缺少它，不算支持旧版本。未提供插件二进制的平台仍可使用 OrcaGym 原有功能，不应在导入阶段强制加载工具。
